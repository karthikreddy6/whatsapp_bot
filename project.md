# OnFood WhatsApp Support Bot

## Purpose

This project is a Node.js service for the OnFood canteen. It combines a
WhatsApp customer-support bot with a live web dashboard for monitoring orders
and support tickets stored in local PostgreSQL (`onfood` database).

## Current Application

The architecture is cleanly separated into two independent services to ensure WhatsApp/Puppeteer browser bugs or crashes never affect the Customer Support Command Center:

1. **Customer Support Service (`support-server.js`)**:
   - Runs independently on port 3000 (`npm run start:support`).
   - Serves the dashboard from `public/` through Express and Socket.IO.
   - Connects to PostgreSQL (`orders`, `order_items`, `users`, `support_tickets`, `support_messages`, `bot_settings`).
   - Handles all dashboard actions, order status changes, ETAs, support tickets, and live chat.
   - Completely free of Puppeteer / Chromium dependencies (zero browser crash risk).
   - Bridges to WhatsApp microservice over HTTP (`http://127.0.0.1:3001`) with graceful fallback when WhatsApp is offline.
   - Relays FastAPI registration OTP requests to the WhatsApp microservice.

2. **WhatsApp Microservice (`whatsapp-service.js`)**:
   - Runs on port 3001 (`npm run start:whatsapp`).
   - Dedicated service for `whatsapp-web.js`, Puppeteer/Chromium, session authentication, and QR display.
   - Sequential rate-limited queue, human typing indicators, and backoff handling.
   - Bot conversational engine (FAQs, status inquiries, problem reports).
   - Forwards inbound messages and ticket creations to Customer Support server via internal HTTP webhooks.

3. **Supervisor Orchestrator (`index.js`)**:
   - Main entry point (`npm start` or `npm run start:all`).
   - Starts Customer Support server in the main process.
   - Spawns WhatsApp microservice as an isolated child process with automatic crash recovery (if WhatsApp crashes or restarts, Customer Support Desk remains 100% online).

## Data Model (PostgreSQL)

- `orders`: `id` (UUID), `user_id`, `status` (`order_status` enum: `PLACED`, `PREPARING`, `READY_FOR_PICKUP`, `DELIVERED`, `CANCELLED`), `total_amount`, `estimated_ready_at`, `created_at`, `updated_at`.
- `order_items`: `id` (UUID), `order_id` (UUID), `menu_item_id` (UUID), `quantity`, `price_at_time_of_order`.
- `users`: `id`, `name`, `phone`, `email`.
- `support_tickets`: `id` (UUID), `user_id`, `order_id`, `subject`, `message`, `status` (`ticket_status` enum: `OPEN`, `IN_PROGRESS`, `RESOLVED`), `created_at`, `updated_at`.
- `support_messages`: `id` (UUID), `ticket_id` (UUID), `sender_type`, `sender_id`, `sender_name`, `message`, `created_at`.
- `bot_settings`: `key` (`config`), `value` (JSONB), `updated_at`.


## Dashboard API

| Method | Endpoint | Action |
| --- | --- | --- |
| GET | `/api/summary` | Returns current dashboard state. |
| PATCH | `/api/orders/:orderId/status` | Updates order status. |
| POST | `/api/orders/:orderId/eta` | Sets an order ETA in minutes from now. |
| POST | `/api/tickets/:ticketId/resolve` | Resolves a ticket. |
| POST | `/api/tickets/:ticketId/reply` | Sends a WhatsApp reply and marks the ticket replied. |
| POST | `/api/buffering-time` | Updates the global ETA buffer. |

## FastAPI OTP Communication

FastAPI owns registration and PostgreSQL. After it creates a pending user, it
calls the bot over the local/private network:

```http
POST http://127.0.0.1:3000/internal/whatsapp/send-otp
x-internal-api-key: <shared private key>
Content-Type: application/json

{
  "phone": "919876543210",
  "otp": "123456",
  "expiresInMinutes": 5
}
```

The bot sends the WhatsApp message and responds with `{ "ok": true }` only
when delivery succeeds. The shared key is generated by
`setup-fastapi-integration.ps1` and stored only in each service's ignored
`.env` file. It is never sent to the Android app or browser.

FastAPI registration endpoints are:

- `POST /api/auth/register` — creates a pending account and triggers OTP
  delivery; it does not issue a login token.
- `POST /api/auth/verify-otp` — verifies the registration code and returns the
  normal login token.
- `POST /api/auth/resend-otp` — sends a replacement OTP after validating the
  pending account credentials.

## Running Locally

```powershell
npm install
$env:ENABLE_WHATSAPP = 'false' # optional: dashboard only
npm start
```

Open `http://localhost:3000/dashboard.html`.

Set `ENABLE_WHATSAPP=true` to initialize WhatsApp Web and scan the QR code.
The service uses the existing `.wwebjs_auth` directory to retain that session.

## Configuration

- `PORT` (default `3000`)
- `ENABLE_WHATSAPP` (enabled unless exactly `false`)
- `CANTEEN_WHATSAPP` (contact notified about stuck orders/tickets)
- `RECENT_WINDOW_MS` (dashboard recent-orders window; default two hours)
- `INTERNAL_API_KEY` (shared secret FastAPI uses when it requests an OTP
  WhatsApp message)

Firebase configuration is currently embedded in both `index.js` and `bot2.js`.

## Known Notes

- The dashboard has no authentication, so it should only be exposed on a
  trusted/internal network until access control is added.
- `start-dashboard.ps1` sets `ENABLE_MOCK_DB`, but `index.js` does not currently
  use that variable; Firebase is still initialized.
- Some legacy text in `bot2.js` and a few strings in the checked-in source show
  mojibake characters, likely from an earlier encoding issue.
